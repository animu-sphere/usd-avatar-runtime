## 2. What `ost` sees of the overlap

`avatarRuntime` packages the core, and `avatarVrmSession` packages the core with the session's
adapters. Both install the `AvatarRuntime` CMake package.
[Issue #77](https://github.com/animu-sphere/usd-avatar-runtime/issues/77) holds the decision to keep
them that way.

Measured locally on Windows with both packaged from one tree, in a scratch `OST_HOME`, and with the
session's six owners pulled by digest:

| Composition | Result |
| --- | --- |
| both packages | `COMPOSITION_INSTALL_PATH_COLLISION` on `bin/avatarRuntime.dll` |
| the session alone, requiring `cmake:AvatarRuntime` | `COMPOSITION_MISSING_PROVIDER` |

The first is what we want, and needs nothing from us. All 18 of the core's files are in the session,
and 17 are byte-identical. Only `bin/avatarRuntime.dll` differs, between two builds of the same source.

Pinned artifacts stay in separate prefixes outside composition, so this check does not reach a
consumer whose search path has both. We handle that in our own CMake configuration, which refuses the
combination, and `scripts/check_package_choice.py` checks it on Windows and Linux. Without the
refusal, this was the failure in the core's configuration, with no reason given:

```text
  but it set AvatarRuntime_FOUND to FALSE so package "AvatarRuntime" is
  considered to be NOT FOUND.
```

## 3. The gap, and why no issue

A library's component contract provides `cmake:<cmake.package>` only, and a descriptor has no way to
declare another CMake package it installs. The session therefore provides `cmake:AvatarVrmSession`
but not `cmake:AvatarRuntime`, although its prefix does satisfy `find_package(AvatarRuntime)`.

This fails closed, as the second row above shows, and a consumer of the session can require
`cmake:AvatarVrmSession` instead. Nothing here composes these packages today. If a composition ever
has to choose a provider of `cmake:AvatarRuntime`, this report is the place to start from.

## 4. Limits

- The compositions ran on Windows only, with locally packaged artifacts rather than published ones.
- Local work used a checksum-verified 0.23.18 in a scratch directory. The `ost` on this machine's
  `PATH` is 0.23.14.
- The Linux result comes from the hosted image with `libx11-dev` and `libxt-dev` provisioned by the
  workflow. The option does not install them, as its documentation says.
